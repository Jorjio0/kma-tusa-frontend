# KMA Tusa — фронтенд

React-фронтенд для афіші студентських тусовок Могилянки: вечірок, квартирників, ночей настолок, караоке тощо. Працює з бекендом [kma-tusa](https://github.com/Jorjio0/kma-tusa) (Django REST).

Зроблено на основі навчального шаблону [fprn_FE_educational_project](https://github.com/SandraRadz/fprn_FE_educational_project): сторінки ресурсів переписані під KMA Tusa, оформлення змінене.

## Як запустити проєкт

Потрібен Node.js 18 або новіший (`node --version`).

1. Запустіть бекенд за інструкцією з [README бекенду](https://github.com/Jorjio0/kma-tusa#як-запустити-проєкт). Він має працювати на http://localhost:8000. Завантажте демо-дані й демо-користувачів: `python manage.py loaddata demo users`.
2. У папці фронтенду встановіть залежності й запустіть сервер розробки:

```bash
npm install
npm run dev
```

3. Відкрийте http://localhost:5173.

Демо-акаунти (з фікстури бекенду `users.json`):

| Логін | Пароль | Роль |
| --- | --- | --- |
| `tusa_student` | `TusaStudent2026` | користувач |
| `tusa_admin` | `TusaAdmin2026` | адміністратор |

Можна також зареєструвати новий акаунт на сторінці **Реєстрація**.

## Порти

| Що | Адреса |
| --- | --- |
| Фронтенд (Vite) | http://localhost:5173 |
| Бекенд (Django) | http://localhost:8000, API: http://localhost:8000/api/ |

Фронтенд звертається до бекенду на `http://localhost:8000`. Якщо бекенд працює на іншій адресі, скопіюйте `.env.example` у `.env`, змініть `VITE_API_URL` і перезапустіть `npm run dev`.

Бекенд дозволяє запити з `http://localhost:5173` і `http://127.0.0.1:5173` через CORS (`CORS_ALLOWED_ORIGINS` у `config/settings.py`). Якщо змінити порт фронтенду, його треба додати й туди.

## Сторінки

| Сторінка | Адреса | Хто бачить | Ресурс API |
| --- | --- | --- | --- |
| Головна | `/` | усі | — |
| Тусовки | `/events` | усі; форма й кнопки редагування лише після входу | `/api/events/` |
| Вхід | `/login` | лише гості | `/api/auth/login/` |
| Реєстрація | `/register` | лише гості | `/api/auth/register/` |
| Мій кабінет | `/profile` | лише залогінені | `/api/auth/me/` |
| Організатори | `/organizers` | лише залогінені | `/api/organizers/` |
| Локації | `/venues` | лише адміністратори | `/api/venues/` |
| Категорії | `/categories` | лише адміністратори | `/api/categories/` |

- На сторінках ресурсів є форма (**Створити** / **Зберегти зміни**), кнопка **Отримати список** і кнопки **Редагувати** та **Видалити** в рядках таблиці.
- На сторінці тусовок категорія, організатор і локація обираються зі списків, які підтягуються з API.
- Помилки валідації від сервера (`400`) показуються під відповідними полями форми, наприклад «Час завершення має бути пізніше за час початку.».
- Помилки `401`, `403`, `404` і `409` показуються над таблицею або формою, наприклад «Неможливо видалити категорію Вечірка: у ній є тусовки (3).».
- Панель **«Відповідь сервера»** у правому нижньому куті показує метод, адресу, статус, тіло й хедери останньої відповіді.

## Авторизація

Бекенд видає JWT-токени: `access` (живе 5 хвилин) і `refresh` (живе 1 добу). Деталі API описано в [README бекенду](https://github.com/Jorjio0/kma-tusa#авторизація-і-права-доступу).

**Вхід і реєстрація.**

- **Вхід.** Сторінка `/login` надсилає `POST /api/auth/login/` і зберігає токени в `localStorage` (`access_token`, `refresh_token`). Потім вона запитує `GET /api/auth/me/`, щоб дізнатися ім'я та роль користувача.
- **Реєстрація.** Сторінка `/register` надсилає `POST /api/auth/register/`, після успіху одразу виконує вхід і відкриває кабінет. Помилки валідації показуються під полями.
- **Запити з токеном.** Кожен запит до API (крім входу, реєстрації та оновлення токена) містить заголовок `Authorization: Bearer <access>`.

**Оновлення токена.** Коли `access` закінчується, сервер відповідає `401`. Тоді `api.js`:

1. надсилає `refresh` на `POST /api/auth/refresh/`;
2. зберігає новий `access`;
3. повторює початковий запит.

Користувач нічого не помічає і не логіниться знову. Якщо кілька запитів отримали `401` одночасно, оновлення виконується один раз. Якщо `refresh` теж недійсний, токени видаляються, і користувача перенаправляє на вхід. Як побачити це вручну: DevTools → Application → Local Storage → змініть `access_token` на будь-який рядок і натисніть **Отримати список**. У вкладці Network буде послідовність `401` → `POST /api/auth/refresh/ 200` → `200`.

**Вихід.** Кнопка **Вийти** видаляє токени з `localStorage` і повертає на головну.

**Поведінка сторінок:**

- Неавторизованого користувача, який відкриває сторінку для залогінених (`/profile`, `/organizers`, `/venues`, `/categories`), перенаправляє на `/login`. Після входу його повертає на сторінку, з якої перенаправило.
- Залогіненого користувача, який відкриває `/login` чи `/register`, перенаправляє в кабінет `/profile`.
- Гість бачить у шапці кнопки **Увійти** і **Реєстрація**. Залогінений користувач бачить своє ім'я (посилання на кабінет) і кнопку **Вийти**.
- Локації й категорії змінює лише адміністратор (`is_staff`). Звичайний користувач на цих сторінках бачить повідомлення «Доступ лише для адміністраторів».

## Структура

```
src/
  api.js              запити до бекенду, токени, оновлення access-токена
  AuthContext.jsx     поточний користувач, вхід і вихід для всього застосунку
  hooks.js            завантаження довідників для випадних списків
  App.jsx             шапка, навігація й маршрути
  components/
    CrudPage.jsx      спільна сторінка: форма + таблиця
    RequireAuth.jsx   захист сторінок: лише для залогінених або адміністраторів
    ResponsePanel.jsx панель «Відповідь сервера»
  pages/
    Home.jsx
    Events.jsx
    Organizers.jsx
    Venues.jsx
    Categories.jsx
    Login.jsx
    Register.jsx
    Profile.jsx
  styles.css
```
